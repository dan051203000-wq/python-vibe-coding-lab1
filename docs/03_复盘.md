# 复盘：哪些交给 AI、哪些自己拍板、哪些风险做了人工审查

## 一、哪些环节交给 AI

1. **代码骨架生成**：两道考题的初始实现（约 90% 的代码行）由 AI 一次生成，
   包括 pandas 清洗管道、FastAPI 路由、Pydantic 校验模型、SQLite 存储层；
2. **测试用例编写**：正常用例 + 边界/异常用例的参数化测试均由 AI 起草；
3. **文档初稿**：README、需求澄清清单的结构与措辞由 AI 按我口述的要点生成；
4. **错误信息文案**：面向用户的报错提示（中文、含定位信息）由 AI 撰写。

## 二、哪些环节自己拍板（不可外包的决策）

1. **需求边界**：6 个字段全部视为"关键字段"（题面说"删除关键字段缺失的行"但未定义哪些是关键字段）——
   我决定全部必需，宁严勿宽；
2. **技术选型**：考题二选 SQLite 而非内存存储——为的是能正面回答"并发写入不产生数据错误"这一验收项，
   同时换来"重启不丢数据"的加分项；
3. **错误契约**：统一 `400 + {"error": {code, message, field}}` 结构，
   而不是接受 FastAPI 默认的 422 + detail 数组——因为题面要求"结构化错误信息"，自定义契约更可验证；
4. **验收口径**：考题一"输出路径=输入路径时拒绝执行"、"原始文件 md5 前后一致"这两条
   AI 最初没做，是我从考题"不得修改原始文件"的约束反推出来补上的。

## 三、哪些风险做了人工审查（AI 输出的 Code Review）

| 风险类型 | 审查发现 | 处置 |
|---|---|---|
| 正确性 | AI 初版 clean() 统计代码自相矛盾（`if False else None` 残留） | 逐行读代码发现，要求重写 |
| 正确性 | generate() 在存在性校验前计算 md5，文件缺失时抛原始异常而非业务报错 | 由测试暴露后修复顺序 |
| 数据一致性 | 数量/单价列若混入文本（"十件"）会在数值比较时静默出错 | 要求 `pd.to_numeric(errors="coerce")` + dropna 显式剔除 |
| 并发安全 | 多线程共享 SQLite 连接会跨线程报错 | 改为每请求独立短连接 + WAL |
| 依赖安全 | pip 依赖未锁版本可能导致评审环境跑不起来 | requirements.txt 声明最低版本约束 |
| 兼容性 | FastAPI `on_event` 已弃用，新版本可能移除 | 改为 lifespan 上下文管理器 |
| 测试有效性 | AI 的测试数据注释与实际插入数据不符（断言 2 条收入实际只有 1 条） | 人工核对数据修正断言，避免"测试通过但测错了东西" |

## 四、对 Vibe Coding 的体会

1. **AI 的输出必须"运行 + 读"双重验证**：本次两个真实缺陷（md5 顺序、统计残留逻辑）
   都不是编译错误，跑起来才知道错；而测试数据注释与代码不符这种问题只有人读才能发现。
2. **小步快跑显著降低返工成本**：每个模块写完立刻测试，缺陷暴露在 10 行代码的范围内，
   而不是 300 行工程里大海捞针。
3. **"把需求讲清楚"本身就是生产力**：需求澄清清单写完后，AI 的实现一次成型率明显提高——
   模糊需求给 AI，返工的是自己。
4. **AI 最该用的地方是"体力活"，最不该让的是"验收标准"**：测试断言的期望值、
   什么叫"正确"、什么叫"安全"，必须自己定。
